单 Reactor 多线程 + 边缘触发的事件驱动服务器

从每连接一线程的阻塞模型出发，经七个版本迭代到单 Reactor 多线程 + 边缘触发 + EPOLLONESHOT 的事件驱动架构。下面记录架构、链路、压测数据， 以及过程中定位到的六个真实问题。

架构

单 Reactor 多线程

一个 epoll 实例同时管理监听 fd 与全部连接 fd。主线程只负责事件收集与任务分发， 不做任何请求处理；worker 线程从任务队列取 fd，完成读写与响应构造后重新武装该 fd。 线程不绑定连接 —— 这是与 V4 之前阻塞模型的根本差别。

  • 主线程 · 事件循环

    epoll_wait 收集就绪事件。监听 fd 就绪时进入非阻塞 accept 循环一次性收割全部新连接；连接 fd 就绪时把 fd 封装为任务投入队列。主线程自身从不阻塞在 socket IO 上。

  • 线程池 · 请求处理

    worker 被唤醒后取出 fd，完成读取、解析、路由、响应构造与发送。工作期间该 fd 处于「已摘除」状态，不会再次被派发。

  • EPOLLONESHOT · 互斥保护

    每个连接 fd 注册时携带 EPOLLONESHOT，事件上报一次后自动失效；worker 收尾时用 EPOLL_CTL_MOD 重新武装。这保证同一 fd 在任意时刻最多只有一个 worker 在操作。

  • 资源回收

    空闲超过 30 秒的连接由定时清理回收；客户端声明 Connection: close 或 HTTP/1.0 且未显式要求长连接时，响应完毕后关闭。

一次请求的完整链路

从 epoll_wait 到字节落网
  • 事件上报

    epoll_wait 返回就绪的 fd 列表与事件掩码。

  • 分支判定

    fd 等于监听 fd → 走 accept 分支；否则是已建立连接的读/写事件 → 走任务派发分支。

  • 读取与分包

    循环 recv 直到 EAGAIN，把数据追加进连接缓冲区。按 \r\n\r\n 切分出完整请求 —— 一次读取可能包含多个请求，也可能只有一个请求的前半段。

  • 解析与路由

    提取请求行的方法与路径、HTTP 版本、Connection 与 If-Modified-Since 头。路径先经 realpath 解析并校验前缀，防止目录穿越。随后进入路由：/、/about、/api/status 或静态文件。

  • 取内容

    静态文件先查 FileCache：命中则直接拿到内存中的 shared_ptr<const string>；未命中则读盘、入库，并把磁盘 mtime 一起带出，供条件请求比对。

  • 协商

    把客户端带来的 If-Modified-Since 与本次实际要返回的正文版本比对。一致则构造 304 响应 —— 不含 Content-Type、Content-Length 与正文。

  • 发送

    拼接响应头与正文，进入 send 循环。若一次未写完，把该 fd 的写事件加入 epoll 监听，可写时继续续发，直到全部落网。

  • 重武装或关闭

    以 EPOLL_CTL_MOD 恢复该 fd 的读事件监听进入下一轮请求；若需关闭则从 epoll 摘除并释放连接资源。任一环节的发送失败都会逐层上报到连接去留决策处。

关键实现

每一条都对应一个具体问题
机制做法解决什么问题
边缘触发 监听与连接 fd 均注册 EPOLLET，读取循环到 EAGAIN 为止 避免水平触发下同一批数据反复唤醒事件循环
EPOLLONESHOT 事件上报后自动失效，处理收尾时 MOD 重武装 同一 fd 被并发派发给两个 worker，导致 double close 或误关已复用的 fd
线程池 mutex + condition_variable + 任务队列 主线程阻塞在 IO 上，并发容量被空闲连接侵蚀
粘包与半包 缓冲区按 \r\n\r\n 切分，未成帧的数据留在缓冲区内等下一次读取 一次 recv 可能拿到多个请求或不完整的请求
缓存共享 正文以 shared_ptr<const string> 返回，映射表由 mutex 保护 一个线程淘汰条目时，另一个线程手上的内容仍然有效
TTL 校验 2 秒窗口内跳过 stat；窗口到期后按纳秒精度比对 mtime 命中路径上的系统调用 —— 让「缓存命中」真正省掉 IO
条件请求 回 Last-Modified，读 If-Modified-Since，命中回 304 重复访问同一静态资源时的整份正文传输
半发送处理 send 部分写入时记录偏移，注册 EPOLLOUT 续发 响应体大于内核发送缓冲区时空闲丢弃已写数据
路径安全 realpath 规范化后校验是否位于站点根目录内 形如 /../../etc/passwd 的目录穿越请求
优雅退出 捕获终止信号后停止 accept，等待在途请求结束再退出 退出瞬间留下半截响应

过程中定位到的六个问题

定位 → 量化 → 修复 → 复测
#现象根因处置
1 V1/V2 突发下约 1 秒长尾 阻塞 accept 每次只取一个连接，backlog 溢出触发客户端 SYN 重传 改 epoll + 非阻塞 accept 循环收割，长尾消失
2 2 条空闲长连接占满 2 个 worker，第 3 条请求延迟 29.8 s epoll 只管监听 fd，已接入连接仍由 worker 阻塞式 recv 独占线程 V5 改为按事件分发而非按连接占用线程，延迟降到 0.24 ms
3 keep-alive 让混合 QPS +23%，P99 却恶化到 21.5 ms 空闲连接直接侵蚀并发容量 结论：keep-alive 必须与事件驱动模型配合，否则得不偿失
4 短连接压测中 5%~35% 的连接被 RST，而服务器日志毫无异常 LT 模式下 worker 尚未 recv 时 epoll 重复上报同一 fd，主线程派发第二个 worker → double close 或误关已复用的 fd 注册 EPOLLONESHOT，失败率从 108/800 归零
5 引入 LRU 缓存后 QPS 测不出提升 923 B 文件预热后完全命中内核页缓存，read() 已接近内存拷贝，缓存只省下一次 open + read 结论：缓存的价值在大文件与磁盘 IO 竞争场景，当前口径覆盖不到 —— 测不出并解释清楚原因，好过编一个数字
6 曾判定 V7 比 V6 下降 19%（两组 6 轮区间不重叠） 口径 A 测量窗口仅 0.03 s，调度抖动足以制造 20% 以上偏差；后经同代码对照发现噪声本底就有 5.7% 放大窗口至 0.7 s 后复测，差异消失，原结论证伪

第 4 与第 6 条是这批改动里最有价值的部分：前者说明「失败率本身就是指标」—— 给压测客户端加上 RST 统计后， 偶发竞态变成了可量化、可复现、可验证归零的数据；后者说明测量窗口必须显著长于被测系统的时间尺度， 且判定版本差异需要一个同代码对照来量化噪声本底。

版本演进

每个版本一个 git tag，可独立检出复现
  • V1
    阻塞 accept + 每连接一线程

    基线实现，响应 Connection: close。

  • V2
    线程池组件

    完成 ThreadPool 类，尚未接入主循环。

  • V3
    epoll 管理监听 fd

    非阻塞 accept 循环一次性收割全部连接，线程池正式接入。混合 QPS 较 V1 提升约 18 倍。

  • V4
    keep-alive 长连接

    连接内循环解析，支持粘包与半包；空闲 30 秒回收。

  • V5
    完整 Reactor 事件驱动

    epoll 同时管理监听与连接 fd，空闲连接不再占用线程；EPOLLONESHOT 修复重复派发竞态。

  • V6
    LRU 文件缓存

    字节上限触发 LRU 淘汰，命中直接返回内存内容。

  • V7
    语义修正

    缓存 mtime 升至纳秒精度、区分 HTTP/1.0 与 1.1 的默认连接方式、头字段名大小写不敏感、发送失败逐层上报。

  • 当前
    运行时统计与条件请求

    新增 /api/status 原子计数接口；缓存改为定期校验，命中路径零系统调用；实现 Last-Modified / If-Modified-Since 协商缓存返回 304。

# 以下命令需在部署本服务器的机器上执行（默认监听 :8080）
H=http://localhost:8080

# 条件请求：第二次询问只回响应头，正文 0 字节
# 期望输出：status=304  bytes=0
LM=$(curl -s -D - -o /dev/null $H/style.css | awk -F': ' 'tolower($1)=="last-modified"{print $2}' | tr -d '\r')
curl -o /dev/null -w 'status=%{http_code}  bytes=%{size_download}\n' \
     -H "If-Modified-Since: $LM" $H/style.css

# 长连接：同一条连接上连续两个请求，第二次复用已建立的连接
# 期望输出：Re-using existing connection!
curl -sv $H/ $H/api/status 2>&1 | grep -E 'Re-using|Connected'

# 运行时统计接口
curl -s $H/api/status
